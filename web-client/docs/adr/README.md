# Architecture Decision Records

ADR фиксируют архитектурные решения веб-клиента AllCash. Вся работа в репозитории идёт по ним. Код не должен противоречить принятым ADR.

## Как работать с ADR

1. Перед задачей прочитайте релевантные ADR, начиная с [0001](0001-web-client-architecture.md).
2. Если задача требует нового или изменённого архитектурного решения, создайте новый ADR до кода или вместе с ним.
3. Скопируйте [0000-template.md](0000-template.md) в `NNNN-kratkoe-nazvanie.md`. Номер — следующий по порядку, четыре цифры. Название — латиницей через дефис.
4. Заполните все разделы шаблона. Статус нового ADR — «Предложено», после согласования — «Принято».
5. Принятые ADR не переписываются. Чтобы изменить решение, создайте новый ADR со статусом «Принято». В старом ADR поставьте статус «Заменено ADR-NNNN». В новом укажите «Заменяет».
6. Добавьте ADR в индекс ниже.

## Когда нужен ADR

- Изменение слоёв или направления зависимостей (`core/*`, `features/*`, `design/`).
- Новая библиотека или замена существующей (роутинг, состояние, хранилище, сборка).
- Изменение модели данных, схемы IndexedDB или протокола синхронизации.
- Изменение стратегии кэширования, PWA или деплоя.
- Новое сквозное правило (деньги, ошибки, именование).

ADR не нужен для исправления бага, рефакторинга внутри слоя и мелких UI-правок.

## Задачи

Формат: `- [ ] Описание — ответственный, ссылка на ADR (если есть)`. Выполненные задачи отмечайте `[x]` и не удаляйте.

- [ ] Перед каждой структурной задачей проверять, не нужен ли новый ADR.
- [ ] При добавлении ADR обновлять индекс выше.
- [ ] При замене ADR обновлять статус старого ADR и поле «Заменяет» в новом.
