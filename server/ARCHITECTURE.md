# Архитектура all-cash-server

Документ описывает устройство серверной части `all-cash` целиком: границы системы, слои, потоки
данных, схему базы и инварианты, которые нельзя нарушать. Решения, из которых эта архитектура
выросла, зафиксированы отдельными записями в `docs/adr/`. Документ отвечает на вопрос «как
устроено», ADR — на вопрос «почему именно так».

Ссылки вида «ADR-0001, п. 5» ведут на пункт 5 записи `docs/adr/0001-backend-architecture.md`.

## 1. Границы системы

```
┌──────────────────┐        HTTP (LAN, X-Login)        ┌──────────────────────┐
│  iOS-клиент,     │ ────────────────────────────────▶ │  all-cash-server     │
│  ../pwa-mobile-client   │ ◀──────────────────────────────── │  cmd/server          │
│  локальная база  │      pull / push / export         └──────────┬───────────┘
└──────────────────┘                                              │ database/sql
                                                       ┌──────────▼───────────┐
                                                       │  SQLite, один файл   │
                                                       │  ALL_CASH_APP_DB_PATH, WAL    │
                                                       └──────────────────────┘
```

Стек — Go, `chi`, SQLite одним файлом без cgo (ADR-0001, п. 1). Сервер — единственный потребитель базы во
время работы. Источник истины для пользователя — база на
устройстве; сервер хранит копию и разрешает конфликты правилом «последняя запись побеждает»
(ADR-0001, п. 7). Наружу сервер не публикуется: он живёт в локальной сети, вход без пароля (ADR-0001, п. 12).

Ролей в системе две: устройство пользователя и администратор, который разворачивает сервер и делает
резервные копии. Межсерверного взаимодействия, фоновых задач и очередей нет.

## 2. Процессы

| Процесс | Точка входа | Назначение |
| --- | --- | --- |
| `server` | `cmd/server/main.go` | HTTP-сервер: синхронизация и выгрузка |

`server` при старте выполняет `migrations/schema.sql` (`CREATE TABLE IF NOT EXISTS`, ADR-0001, п. 4).
Существующие таблицы он не меняет.

Запуск `server`: чтение настроек → настройка `slog` → открытие базы → сборка `usecase` → сборка
HTTP-сервера → ожидание `SIGINT`/`SIGTERM` → `Shutdown` с таймаутом `ALL_CASH_SERVER_SHUTDOWN_TIMEOUT`.
Ошибка на любом шаге до прослушивания порта валит процесс с кодом 1.

## 3. Слои

```
cmd/server ──────────── сборка зависимостей, сигналы, логгер
      │
internal/transport/http ─ роутер chi, middleware, хендлеры, JSON
      │  интерфейс Usecase объявлен здесь
internal/usecase ──────── бизнес-правила, семантические проверки, CSV
      │  интерфейс Repository объявлен здесь
internal/repository ───── SQLite: SQL, seq, сканирование строк
      
internal/models ───────── структуры домена, DTO запросов и ответов, коды ошибок
migrations ────────────── schema.sql, вшитый в бинарник
```

Зависимости направлены строго вниз. Интерфейс объявляет тот, кто его вызывает, а не тот, кто его
реализует (ADR-0001, п. 2): `transport` описывает нужный ему `Usecase`, `usecase` описывает нужный ему
`Repository`. `models` не зависит ни от кого.

`models` умышленно содержит и домен (`Account`, `Operation`), и DTO (`AccountRequest`,
`OperationResponse`), и таблицу кодов ошибок. Теги `json` в DTO — единственное описание проводного
формата; поля API называются camelCase, столбцы базы — snake_case (ADR-0001, п. 22). Домен маленький и один на весь проект, поэтому
разделение на три пакета дало бы каталоги вместо ясности.

### 3.1 internal/transport/http

`http.go` собирает роутер и `http.Server`. Порядок middleware: `RequestID` → `Recoverer` →
`logging` → `cors` → `limitBody`. Закрытые ручки собраны в `chi.Group` с `authorize`.

Заголовки источника и ответ на preflight даёт `cors.Handler` из `github.com/go-chi/cors`; его
настройки — списки методов, заголовков и `preflightMaxAge` в `middleware.go` (ADR-0001, п. 23).

`middleware.go` держит `limitBody` (ограничение тела 10 МиБ, ADR-0001, п. 21), `authorize` (разбор
`X-Login`, ADR-0001, п. 11), `logging` (строка на запрос, ADR-0001, п. 16) и два значения в контексте запроса:
`session` и `logEntry`.

Запрос `OPTIONS` дальше `cors` не проходит: `cors.Handler` отвечает на preflight сам. Ручек
`OPTIONS` в роутере нет.

`handlers.go` разбирает запрос через общий `decodeJSON`, вызывает `usecase`, переводит его ошибки в коды ответа и пишет JSON.
Бизнес-правил в хендлерах нет; единственное решение, которое они принимают сами, — какой код ошибки
соответствует какой ошибке уровня `usecase`. Связь кода ошибки со статусом HTTP и сообщением задана
одной таблицей `models.errorSpecs` (ADR-0001, п. 17); тело ошибки всегда имеет вид
`{"error": {"code": ..., "message": ...}}`.

### 3.2 internal/usecase

`usecase.go` — аутентификация, регистрация, `Pull`, `Push` и семантические проверки. Проверки
возвращают строку-причину отказа, а не `error` (ADR-0001, п. 8): `error` из этого слоя означает сбой
инфраструктуры и превращается в 500.

`export.go` — сборка CSV (ADR-0001, п. 14).

Состояние слоя: репозиторий, `pullLimit` и функция `now`. Подменяемое `now` позволяет проверять
границы дат без ожидания реального времени.

### 3.3 internal/repository

Один тип `Repository` поверх `*sql.DB`. Пул ограничен одним соединением (ADR-0001, п. 3), поэтому
последовательность «прочитать `MAX(seq)` — записать строку» внутри транзакции безопасна без
дополнительных блокировок.

Записи идут через общий помощник `save`, который открывает транзакцию, выделяет `seq`, вызывает
переданную функцию записи и фиксирует транзакцию. Три метода `Save*` отличаются только текстом
`INSERT ... ON CONFLICT DO UPDATE`.

Чтение строк идёт через `scanAccount`, `scanCategory`, `scanOperation` — они принимают интерфейс
`scanner`, поэтому один код обслуживает и `QueryRow`, и `Rows`. Строка `sql.ErrNoRows` переводится в
`models.ErrNotFound`: остальные слои про `database/sql` не знают.

## 4. Схема базы

Четыре таблицы: `users`, `accounts`, `categories`, `operations`.

Первичный ключ справочников и операций — составной, `(id, user_id)`. Идентификаторы генерирует
клиент (UUID), поэтому сервер не умеет их выдавать и не должен: строка приходит с устройства вместе
с данными. Составной ключ и составные внешние ключи `(account_id, user_id) → accounts(id, user_id)`
не дают операции одного пользователя ссылаться на счёт другого (ADR-0001, п. 6).

Особые столбцы каждой синхронизируемой таблицы:

- `seq INTEGER NOT NULL` — курсор синхронизации, уникален в пределах пользователя (ADR-0001, п. 5);
- `deleted_at TEXT` — мягкое удаление, `NULL` означает живую запись (ADR-0001, п. 7);
- `updated_at TEXT NOT NULL` — время последней записи на сервере, служебное поле для разбора
  инцидентов; клиенту не отдаётся.

Индексы: `idx_*_seq` (уникальный, `user_id, seq`) обслуживает `/pull` и держит инвариант курсора;
`idx_operations_user_date` — сортировку выгрузки; `idx_operations_debt` — подсчёт погашений;
`idx_operations_live` — выборку живых операций.

Денежные суммы и время хранятся текстом (ADR-0001, п. 13). `is_archived` и `is_hidden` — `INTEGER` 0/1.
`is_hidden` означает «не показывать сумму счёта в клиенте»; поле необязательное в `/push`, при
отсутствии считается `false`.

Долг и его погашения связаны внутри одной таблицы: `operations.debt_id` ссылается на
`operations(id, user_id)`. Отдельной таблицы долгов нет — долг это операция вида `debt`.

## 5. Потоки данных

### 5.1 GET /pull?since=N&limit=M

1. `authorize` находит пользователя по `X-Login`.
2. Хендлер разбирает `since` (обязателен, ≥ 0) и `limit` (необязателен, > 0).
3. `usecase.Pull` подставляет `ALL_CASH_APP_PULL_LIMIT` вместо пустого `limit` и обрезает его потолком 5000.
4. `repository.Changes` выбирает из трёх таблиц строки с `seq > since`, по `limit + 1` из каждой.
   Если суммарно строк больше `limit`, он находит `limit`-ю по возрастанию `seq` среди всех трёх
   выборок и отсекает всё, что больше этой границы, выставив `hasMore`. Так страница никогда не
   рвётся внутри одного `seq`.
5. `usecase` считает `nextSeq` как максимальный `seq` отданных строк; если отдавать нечего,
   `nextSeq` остаётся равным `since`.
6. Ответ — `nextSeq`, `hasMore` и три массива. Пустой массив отдаётся именно массивом, не `null`.

### 5.2 POST /push

1. `authorize` находит пользователя.
2. Хендлер декодирует тело и проверяет каждую запись синтаксически (ADR-0001, п. 8). Ошибка в счёте или
   категории обрывает весь запрос ответом 422 `schema_error`; ошибка в операции попадает в
   `rejected` и не мешает остальным (ADR-0001, п. 9).
3. `usecase.Push` сохраняет счета, затем категории, затем операции. Операции переупорядочены так,
   что `debt` идут первыми (ADR-0001, п. 10).
4. Для каждой записи выполняются семантические проверки; отклонённая запись попадает в `rejected`,
   сохранённая — в `accepted` вместе с выданным `seq`. Мягко удалённая запись проверки пропускает.
5. Ответ — 200 с `accepted`, `rejected` и `finishedAt`. Курсор клиента `/push` не двигает никогда.

Каждая запись сохраняется своей транзакцией. Батч целиком не атомарен: это прямое следствие
частичного успеха (ADR-0001, п. 9).

### 5.3 GET /health

Открытая ручка без `X-Login`: `usecase.Health` проверяет базу, `healthcheck` в Compose опрашивает её.

### 5.4 GET /export/csv

`usecase.ExportCSV` читает живые операции и четыре справочные карты (имена счетов, имена категорий,
контрагенты долгов, направления долгов) — пять запросов на всю выгрузку, без запроса на строку.
Дальше собирает файл в памяти и отдаёт его как вложение с именем `operations-ГГГГ-ММ-ДД.csv`.

### 5.5 Аутентификация и регистрация

`/auth/login` и `/auth/register` открыты. Логин нормализуется `models.NormalizeLogin` (обрезка по
краям и нижний регистр) во всех трёх точках: логин, регистрация, `authorize`. Неизвестный логин в
заголовке даёт 401 `invalid_token`, неизвестный логин на `/auth/login` — 401 `unknown_login`
(ADR-0001, п. 11).

## 6. Инварианты

Нарушение любого из них — ошибка, а не компромисс:

1. `seq` уникален в пределах пользователя и растёт монотонно по всем трём таблицам сразу.
2. Курсор двигает только `/pull`.
3. Схему создаёт только `repository.New` при старте; существующие таблицы не меняются.
4. Записи выдаются и читаются только в границах `user_id`; ни один запрос данных не выполняется без
   `user_id` в условии.
5. Удаление всегда синхронизируется: мягко удалённая запись не проходит проверки и не может быть
   отклонена.
6. Денежная сумма никогда не превращается во `float`.
7. Время в базе и в API всегда UTC.
8. Логины, заголовки сессии и тела запросов не попадают в логи.

## 7. Настройки и развёртывание

Две группы: `ALL_CASH_APP_` — приложение, `ALL_CASH_SERVER_` — HTTP. Обязательна одна переменная — `ALL_CASH_APP_DB_PATH`.
Остальные имеют значения по умолчанию в тегах структуры `internal/config`. Файл `.env` подхватывается
автоматически, реальная переменная окружения перекрывает файл (ADR-0001, п. 15).

Образ Docker собирается в две стадии, содержит один статический бинарник и работает под
непривилегированным пользователем (ADR-0001, п. 20). `docker-compose.yml` описывает сервис `server`
(ADR-0001, п. 20). Второй сервис, `web`, собирает `../pwa-mobile-client` и к серверу не относится.

Настройки оба сервиса получают через `env_file: .env` (файл лежит в корне репозитория, рядом с `docker-compose.yml`; `make` в `backend/` подключает его как `../.env`) — тот же файл, что читает `godotenv` при
локальном запуске. База хранится в каталоге хоста: `${ALL_CASH_DATA_DIR:-./data}` смонтирован в `/app/data`,
рабочий каталог контейнера — `/app`, поэтому относительный `ALL_CASH_APP_DB_PATH=./data/all_cash.db` верен и
на хосте, и в контейнере. Порт по умолчанию привязан к `127.0.0.1`; `ALL_CASH_BIND_ADDRESS` открывает его
локальной сети, `ALL_CASH_SERVER_PORT` одинаков внутри и снаружи (ADR-0001, п. 20).

`ALL_CASH_SERVER_CORS_ORIGINS` перечисляет источники страниц, которым браузер разрешает читать ответы сервера;
по умолчанию `*` — любой (ADR-0001, п. 23). Это не аутентификация: доступ к данным даёт только `X-Login`.

## 8. Тестирование

Тестами покрыт только `usecase` (ADR-0001, п. 18). Репозиторий там мокается: `mocks_test.go` — рукописный
мок, который падает по `t.Fatalf` на любой неожиданный вызов, поэтому тест фиксирует не только
результат, но и набор обращений к базе. Генератор моков не используется.

Тестов `repository`, `config` и транспортного слоя нет и не планируется. Новое правило добавляется
тестом в `internal/usecase`; если для проверки понадобилась база, значит правило оказалось не в том
слое. Изменения в SQL проверяются вручную через `api.http`.

## 9. Язык текстов

Тексты, которые видит пользователь, — по-русски: причины отказа, сообщения проверок, сообщения об
ошибках API, заголовок и названия типов операций в CSV. Тексты, которые видит только разработчик, —
по-английски: обёртки `fmt.Errorf`, сообщения и имена полей `slog`, комментарии. Имена тестов и
сообщения о падении тестов — по-русски (ADR-0001, п. 19).

Причины отказа и сообщения об ошибках являются частью контракта с клиентом: их переформулировка видна
пользователю и не считается рефакторингом.

## 10. Известные пробелы

Список того, что сознательно не сделано или не доделано. Это не ошибки в документе, а материал для
будущих задач.

1. `api.http` указывает на порт 8080, `ALL_CASH_SERVER_PORT` по умолчанию 8000.
2. Ограничения частоты запросов нет; при выносе сервера наружу оно понадобится вместе с закрытием
   `/auth/register` (ADR-0001, п. 12).
3. Версия Go задана в двух местах — `Dockerfile` и `go.mod` — и расходится молча; сейчас в обоих
   1.26.0.
4. Регрессия в SQL тестами не отлавливается: тестами покрыт только `usecase` (ADR-0001, п. 18).
5. Список методов и заголовков CORS задан константами в `middleware.go` и с роутером не сверяется
   (ADR-0001, п. 23): новая ручка с другим методом потребует правки вручную.
