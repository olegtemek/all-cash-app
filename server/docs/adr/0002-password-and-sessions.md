# ADR-0002: Вход по паролю и серверные сессии

- Статус: Принято
- Дата: 2026-09-30
- Заменяет: ADR-0001, п. 11 целиком; п. 23 в части заголовков CORS; отклонённый вариант «Пароль или токен вместо голого логина»

## Контекст

По ADR-0001, п. 11 доступ к данным давал заголовок `X-Login` с голым логином: любой, кто знает логин и достаёт до сервера, читает и пишет чужие данные. Нужен вход по паролю. Отдельное требование владельца: открытая сессия не должна слетать — ни по времени, ни после перезапуска сервера, ни при потере сети. При этом выход с устройства должен действительно закрывать доступ.

## Решения

### 1. Пароль

- `POST /auth/register` и `POST /auth/login` принимают `{"login", "password"}`. Длина пароля — от `models.MinPasswordLen` (6) до `models.MaxPasswordLen` (256) символов; нарушение даёт `400 bad_request` с текстом причины.
- Хеш — argon2id из `golang.org/x/crypto/argon2`, параметры OWASP: память 19 МиБ, 2 прохода, 1 поток, соль 16 байт, ключ 32 байта. Формат — строка PHC `$argon2id$v=19$m=19456,t=2,p=1$<соль>$<ключ>`. Параметры хранятся в хеше, поэтому их можно поднять без миграции.
- Хеширование и проверку выполняет `usecase` (`internal/usecase/auth.go`); сравнение — за постоянное время. `repository` получает и хранит только готовый хеш.
- Неверный пароль на `/auth/login` — `401 wrong_password`. Неизвестный логин — по-прежнему `401 unknown_login`.

### 2. Хранение пароля

- Хеш хранится в столбце `users.password_hash TEXT NOT NULL`, отдельной таблицы для учётных данных нет. `repository.CreateUser` пишет пользователя вместе с хешем, `UserByLogin` возвращает хеш в `models.User.PasswordHash`.
- Обратной совместимости с базой без паролей нет. `schema.sql` не изменяет существующую таблицу `users` (ADR-0001, п. 4), поэтому базу, созданную до этого ADR, нужно пересоздать: удалить файл SQLite и завести пользователей заново через `/auth/register`, данные вернуть синхронизацией с устройства.

### 3. Сессии

- Каждый успешный вход и регистрация открывают новую сессию. Ответ содержит поле `token`: 32 случайных байта в base64url, непрозрачная строка без данных внутри.
- Таблица `sessions(token_hash, user_id, created_at)`. В базе лежит SHA-256 токена, не сам токен: утёкшая база не даёт войти. Медленный хеш токену не нужен — у него 256 бит энтропии.
- Защищённые ручки (`/pull`, `/push`, `/export/csv`, `/auth/logout`, `/auth/logout-all`) принимают только `Authorization: Bearer <token>`. `X-Login` больше не принимается.
- Срока действия у сессии нет. Она живёт, пока её не закроет `POST /auth/logout` (текущая сессия) или `POST /auth/logout-all` (все сессии пользователя, включая текущую). Обе ручки отвечают `204`.
- Неизвестный или закрытый токен даёт `401 invalid_token`. Коды `invalid_token`, `unknown_login` и `wrong_password` не смешиваются.

### 4. CORS

- `AllowedHeaders`: `Content-Type`, `Authorization` (вместо `X-Login`). Остальное в ADR-0001, п. 23 без изменений.

## Последствия

- Доступ к данным требует пароля. Сессия переживает перезапуск сервера и любое время без сети.
- Выход отзывает сессию одного устройства, `/auth/logout-all` — все сессии пользователя, например после потери устройства.
- Перехваченный токен действует, пока сессию не закроют. От перехвата защищает только транспорт: HTTPS не встроен, поэтому ограничение ADR-0001, п. 12 (только локальная сеть, HTTPS на прокси при выходе наружу) остаётся в силе.
- Каждый защищённый запрос делает один запрос к `sessions` с `JOIN users`.
- Строки `sessions` копятся: сессия устройства, с которого не вышли, не удаляется никогда.
- Новая зависимость `golang.org/x/crypto` (ADR-0001, п. 1): argon2id — рекомендованный алгоритм хеширования паролей, в стандартной библиотеке его нет.
- Старые клиенты (iOS-приложение и веб-клиент до ADR-0004 веб-клиента) перестают синхронизироваться, пока не перейдут на пароль и `Authorization`.
- Существующая база требует пересоздания (п. 2).
- `/auth/register` по-прежнему открыт.

## Отклонённые варианты

- Бессрочный JWT: отозвать один токен нельзя, выход с устройства доступ не закрывает; нужен и секрет подписи, и его хранение. Перехват опасен одинаково для JWT и для токена сессии, но сессию хотя бы можно закрыть.
- Короткий access-токен плюс refresh-токен: сложнее и на клиенте, и на сервере, а требование «сессия не слетает» сводит его к бессрочному refresh-токену — то есть к той же сессии.
- Сессия со сроком действия или скользящим сроком: устройство, долго бывшее без сети, разлогинилось бы.
- PBKDF2 из стандартной библиотеки: без зависимости, но слабее argon2id против перебора на GPU.
- Отдельная таблица `credentials`: лишняя сущность ради одного поля, нужна только для совместимости со старыми базами, а совместимость не требуется.
- Задание пароля первым входом для пользователей без пароля: открывает окно, в котором пароль задаёт тот, кто войдёт первым.
