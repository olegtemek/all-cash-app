# ADR-0001: Архитектура сервера all-cash

- Статус: Принято
- Дата: 2026-09-30

## Контекст

`all-cash-server` — серверная часть личного финансового приложения AllCash. Сервер хранит копию данных каждого пользователя, синхронизирует её с устройствами в обе стороны и отдаёт выгрузку в CSV. Клиентов два: нативный iOS-клиент и веб-клиент (`../pwa-mobile-client`, PWA). Источник истины — база на устройстве; сервер разрешает конфликты правилом «последняя запись побеждает».

Нагрузка — единицы запросов в минуту, объём данных — десятки тысяч операций за годы. Сервер разворачивает сам владелец на домашней машине или в контейнере.

Этот ADR фиксирует текущие архитектурные решения. Как система устроена целиком, описано в `../../ARCHITECTURE.md`; здесь только причины. Новые решения оформляются отдельными ADR (`0002-...`, `0003-...`) и ссылаются на этот файл, если меняют или отменяют его пункты.

## Решения

### 1. Стек: Go, chi, SQLite без cgo

- Go, маршрутизатор `chi`, SQLite одним файлом через `modernc.org/sqlite` (чистый Go), деньги — `shopspring/decimal`.
- `chi` совместим с `net/http`: middleware и хендлеры остаются стандартными функциями.
- `modernc.org/sqlite` вместо `mattn/go-sqlite3` ради `CGO_ENABLED=0`: статическая сборка, работа в `alpine` без libc.
- Список зависимостей в `go.mod` короткий; каждая новая требует обоснования.

### 2. Три слоя, интерфейс объявляет потребитель

```
transport/http  ->  usecase  ->  repository
                  models (домен, DTO, коды ошибок) — ни от кого не зависит
```

- `transport` объявляет нужный ему `Usecase`, `usecase` объявляет нужный ему `Repository`.
- Зависимости направлены только вниз.
- Сборка зависимостей — в `cmd/server/main.go`: настройки → репозиторий → usecase → HTTP-сервер.

### 3. Один файл SQLite и одно соединение в пуле

- `repository.New` ставит `SetMaxOpenConns(1)`.
- Последовательность «прочитать `MAX(seq)` — записать строку» внутри транзакции безопасна без дополнительных блокировок.
- DSN (`busy_timeout`, `journal_mode(WAL)`, `foreign_keys(ON)`) задан в `repository.dsn`.
- Запускать одновременно `make run` и контейнер на одном файле не нужно.

### 4. Схему создаёт server при старте

- `repository.New` выполняет `migrations/schema.sql` (вшит через `go:embed`) при каждом старте. Скрипт идемпотентен (`IF NOT EXISTS`).
- Существующие таблицы не изменяются: новый столбец в уже созданной базе добавляется вручную.
- Таблицы версий нет. Переименование, удаление столбца и смена типа не поддерживаются и требуют отдельного ADR.

### 5. Курсор синхронизации — общий per-user `seq`

- Один монотонный `seq` на пользователя для `accounts`, `categories`, `operations`. `repository.nextSeq` считает `MAX(seq) + 1` по объединению трёх таблиц внутри транзакции записи.
- Курсор двигает только `GET /pull`. `POST /push` его не двигает.
- `repository.Changes` берёт `limit + 1` строк из каждой таблицы и режет по `limit`-му наименьшему `seq`, чтобы страница не рвалась внутри одного `seq`.
- `usecase.Pull` подставляет `ALL_CASH_APP_PULL_LIMIT` вместо пустого `limit` и ограничивает его потолком 5000.

### 6. Составные ключи с `user_id`

- Первичный ключ `(id, user_id)`; внешние ключи тоже составные, например `(account_id, user_id) → accounts(id, user_id)`.
- Идентификаторы (UUID) генерирует клиент.
- Операция одного пользователя не может сослаться на запись другого на уровне схемы. Ни один запрос данных не выполняется без `user_id` в условии.

### 7. Мягкое удаление и «последняя запись побеждает»

- Удаление мягкое: `deleted_at`, `NULL` — живая запись. Строки физически не удаляются.
- Запись применяется через `INSERT ... ON CONFLICT(id, user_id) DO UPDATE`; версии не сравниваются, устаревшие записи не отклоняются.
- Мягко удалённая запись проходит без проверок, поэтому удаление всегда синхронизируется.

### 8. Две стадии проверки

- Синтаксис — в `internal/models/requests.go` (`Validate()` + `ToModel()`): форма UUID, enum, даты RFC3339, разбор десятичных, набор полей по `kind` (`requiredFields`, `checkFieldSet`).
- Семантика — в `internal/usecase`: существование счёта, совпадение валют, тип категории, погашения не больше долга, разные счета перевода.
- Семантические проверки возвращают строку-причину отказа (константы `reason*`), а не `error`. `error` из `usecase` означает сбой инфраструктуры и даёт 500.

### 9. Частичный успех push

- `POST /push` отвечает 200 с `accepted` и `rejected`, даже если часть записей отклонена.
- Ошибка формы в счёте или категории обрывает весь запрос: 422 `schema_error`.
- Ошибка в операции попадает в `rejected` по id, остальные сохраняются.
- Каждая запись сохраняется своей транзакцией; батч целиком не атомарен.

### 10. Долги обрабатываются в батче первыми

- `usecase.sortOperations` ставит операции `kind == "debt"` в начало, чтобы погашение из того же push нашло свой `debt_id`.
- Отдельной таблицы долгов нет: долг — операция вида `debt`, погашения ссылаются на неё через `operations.debt_id`.

### 11. Аутентификация по логину без пароля

- Заголовок `X-Login` на `/pull`, `/push`, `/export/csv`. Middleware `authorize` находит пользователя и кладёт `session` в контекст.
- Логин нормализуется `models.NormalizeLogin` (обрезка и нижний регистр) везде: `/auth/login`, `/auth/register`, `authorize`.
- Два разных 401: `invalid_token` (клиент сбрасывает сессию) и `unknown_login` (клиент показывает ошибку на экране входа). Не смешивать.

### 12. Только локальная сеть

- Порт наружу не публикуется. `POST /auth/register` открыт и не защищён.
- Перед выходом наружу нужны: VPN или список IP или Basic Auth на прокси, закрытие `/auth/register`, HTTPS.
- Compose привязывает порт к `127.0.0.1`; `ALL_CASH_BIND_ADDRESS` открывает его локальной сети.

### 13. Деньги и время — строки

- Деньги: `shopspring/decimal`, в базе и JSON — строка через `StringFixed(2)`. `float` не используется.
- Время: в базе `time.RFC3339Nano` в UTC; в API `models.TimeLayout` (`2006-01-02T15:04:05.000Z`) через `models.FormatTime` и `FormatOptionalTime`.
- Nullable-столбцы — через `sql.NullString`, `optionalString`, `parseOptionalTime`.

### 14. CSV для Excel

- UTF-8 BOM, разделитель `;`, окончания строк CRLF, запятая как десятичный разделитель.
- Только живые операции. Имена подставляются из четырёх справочных карт, загруженных заранее, а не запросом на строку.
- Файл собирается в памяти и отдаётся как вложение `operations-ГГГГ-ММ-ДД.csv`.

### 15. Настройки: cleanenv и `.env`

- Группы: `ALL_CASH_APP_` (приложение) и `ALL_CASH_SERVER_` (HTTP). Обязательна только `ALL_CASH_APP_DB_PATH`.
- Значения по умолчанию заданы в тегах `internal/config`. Файл `.env` читает `godotenv/autoload`; реальная переменная окружения важнее файла.
- Один файл `.env` в корне репозитория используют `make` (`include ../.env`), `docker compose` (`env_file`) и оба бинарника.

### 16. Структурный лог без персональных данных

- `log/slog`, JSON, одна строка на запрос из middleware `logging`.
- Хендлеры дополняют строку через `logEntryFrom`: `since`, `next_seq`, `records`, `accepted`, `rejected`.
- Логины, заголовки сессии и тела запросов в лог не попадают.

### 17. Единая таблица кодов ошибок

- `models.errorSpecs` связывает `ErrorCode` со статусом HTTP и сообщением. Хендлеры вызывают `respondErrorCode` и `respondError`.
- Тело ошибки: `{"error": {"code": ..., "message": ...}}`. Новый вид ошибки добавляется в эту таблицу.
- Внутренние ошибки логирует `Server.fail`; клиент получает `internal_error` без деталей.

### 18. Тестируется только usecase

- Тесты есть только в `internal/usecase`, на рукописном моке `Repository` (`mocks_test.go`), который падает по `t.Fatalf` на неожиданный вызов. Генератора моков нет.
- Тестов `repository`, `config` и транспорта нет. Правило, которому для проверки нужна база, стоит не в том слое.
- SQL проверяется вручную через `api.http`.
- Подменяемая функция `now` в `usecase` позволяет проверять границы дат.

### 19. Язык текстов

- Русский: причины отказа, сообщения проверок и ошибок API, CSV, документация, имена и сообщения тестов.
- Английский: обёртки `fmt.Errorf`, сообщения и поля `slog`, комментарии в коде.
- Причины отказа и сообщения об ошибках — часть контракта с клиентом; их правка не считается рефакторингом.

### 20. Docker и Compose

- Образ в две стадии, `CGO_ENABLED=0`, статический бинарник `server`, непривилегированный пользователь `allcash` (uid 10001).
- `docker-compose.yml` в корне репозитория: сервис `server`, плюс `web` для веб-клиента. `healthcheck` опрашивает `/health`; `stop_grace_period` 15s больше `ALL_CASH_SERVER_SHUTDOWN_TIMEOUT`.
- База лежит в каталоге хоста: `${ALL_CASH_DATA_DIR:-./data}` смонтирован в `/app/data`; рабочий каталог контейнера `/app`, поэтому относительный `ALL_CASH_APP_DB_PATH=./data/all_cash.db` верен и на хосте, и в контейнере. Именованных томов нет.
- `ALL_CASH_DOCKER_USER` задаёт uid:gid процесса, когда владелец каталога данных на хосте другой.

### 21. Ограничение тела запроса

- Middleware `limitBody`: 10 МиБ (`maxBodyBytes`). Заявленный `Content-Length` больше лимита сразу даёт `413 payload_too_large`; тело без него обрезается `http.MaxBytesReader`.
- Каждое JSON-тело читается через `decodeJSON`: `http.MaxBytesError` → `413 payload_too_large`, любая другая ошибка → `400 bad_request`. Напрямую тело не декодировать.

### 22. JSON в camelCase

- Поля API — camelCase (`initialBalance`, `nextSeq`, `hasMore`). Теги `json` в `requests.go` и `responses.go` — единственное описание проводного формата.
- Столбцы базы и ключи лога остаются snake_case.

### 23. CORS для веб-клиента

- Порядок middleware: `RequestID` → `Recoverer` → `logging` → `cors` → `limitBody`.
- Используется `github.com/go-chi/cors`. Источники — `ALL_CASH_SERVER_CORS_ORIGINS` (по умолчанию `*`), методы `GET`, `POST`, `OPTIONS`, заголовки `Content-Type` и `X-Login`, `ExposedHeaders` — `Content-Disposition`, `MaxAge` 600 с, `AllowCredentials` `false`.
- Preflight не доходит до `authorize`; ручек `OPTIONS` в роутере нет.
- CORS не аутентификация: доступ к данным даёт только `X-Login`.
- Списки методов и заголовков в `middleware.go` с роутером не сверяются: новая ручка с другим методом требует правки вручную.

## Последствия

- Сборка без компилятора C, образ маленький, разворачивание — один бинарник и один файл базы.
- Один пользователь пишет и читает без блокировок, но запись сериализована одним соединением.
- Пока нет тестов `repository` и транспорта, регрессия в SQL или в роутинге ловится только вручную.
- Вход без пароля и открытый `/auth/register` допустимы только в локальной сети (п. 12).
- Батч `push` не атомарен: клиент обязан разбирать `rejected` по каждому id.
- Схема растёт добавлением столбцов; любое другое изменение схемы требует нового ADR.

## Отклонённые варианты

- PostgreSQL: отдельный процесс и обслуживание ради одного пользователя.
- `mattn/go-sqlite3`: требует cgo и тянет libc в образ.
- Библиотека миграций (`goose`, `golang-migrate`): зависимость и формат файлов ради схемы из четырёх таблиц.
- Пароль или токен вместо голого логина: сознательно не делается, пока сервер живёт только в локальной сети.
- Атомарный push «всё или ничего»: одна плохая операция блокировала бы синхронизацию всех остальных.
- Именованный том Docker для базы: файл недоступен обычными средствами хоста.
- Тесты `repository` на настоящем SQLite: отказались в пользу тестов только слоя `usecase`.
- Собственное CORS-middleware: не различает регистр и схему и отвечает 204 на любой preflight.
